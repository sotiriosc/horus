# Queue and concurrency audit

The promoted policy source is a decision function, not an asynchronous dispatcher. In the controlled-pairing worker, a matched inactive boundary issues exactly one model call; a triggered S escape issues no S model call. Diverged I and S decisions execute in source order, followed by separate protected world executions. The eligibility campaign invokes one case command with blocking subprocess.run, then audits it before the next case. The grounded-authority autonomous worker also loops decisions serially. The examined sources do not start concurrent inference workers or use a thread/process pool for action calls.

The action-model reproducibility audit uses a sampling thread to observe OS processes while a call runs, and calls /api/tags for model identity before calls; the sampler does not issue generation requests. This benchmark samples nvidia-smi and /proc only. No overlapping benchmark requests were sent. Ollama 0.1.16 lacks ollama ps and /api/ps here, so runner state was read from /proc and logs.

Ollama-reported total_duration excludes some client/network/scheduling time. The benchmark's warm wall-minus-total differences were roughly 0.002–0.047 s. Read-only aggregates of the archived controlled-pairing and eligibility call metadata found median differences of 0.004 s and 0.024 s respectively; maxima were 0.051 s and 0.048 s. None of the 100 unique archived attempts exceeded one second of external wait. Those numbers do not support queueing as a material bottleneck in the completed campaigns. The full 30-decision review-shaped probe did not return after 900 s, so its internal queue/prompt/generation phase split is unavailable; during that interval its dedicated runner was observed actively using about 16 CPU cores and high GPU utilization. Do not count the whole timeout as measured queue wait.

A shared old Ollama server can still queue a request if another worker or unrelated client is active. A future production dispatcher should serialize or isolate workloads deliberately and record client wall time beside server total_duration. No concurrency configuration or historical harness was changed in this milestone.
